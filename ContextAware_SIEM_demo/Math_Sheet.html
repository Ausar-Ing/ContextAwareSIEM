Step 3The raw score s

s = 2−E[ℓ] / c(ψ)
c(ψ) = 2 H(ψ − 1) − 2 (ψ − 1) / ψ,   H(i) = 1 + ½ + … + 1/i ≈ ln i + 0.5772

Every symbol

ℓ (the "cuts")
The path length: how many random cuts one tree needs to set this window apart from the other windows it was grown from. A cut picks one of the 14 features at random and a random value between that feature's lowest and highest value in the current group, and splits the group in two. Cuts repeat until the window is alone. If a leaf still holds several training windows, the expected number of further cuts is added (scikit-learn's standard allowance).
E[ℓ]
The average of ℓ over the forest's 200 trees.
ψ
How many windows each tree is grown from: min(4096, n) for n training windows. Here all of them: 1,138 in russellmitchell, 2,873 in harrison.
c(ψ)
The average number of cuts a window needs in a random tree of ψ windows (the average unsuccessful search in a binary search tree). It sets the scale: 13.23 for russellmitchell, 15.08 for harrison.
H(i)
The harmonic number. ln is the natural logarithm, 0.5772 is Euler's constant.
s
The raw score, between 0 and 1. Close to 1: cut off almost at once, so unusual. 0.5: an average number of cuts. Below 0.5: hard to separate, so ordinary.

Why it has this shape

  • Few cuts means unusual. A window unlike the others sits in an empty part of the feature space, so a random cut separates it early. Counting cuts needs no attack labels.
  • Dividing by c(ψ) removes the tree size. 4.8 cuts means a lot in a tree of 1,138 windows and little in a tree of 40. The ratio E[ℓ] / c(ψ) is "cuts compared with an average window".
  • 2 to the minus that ratio puts it on 0 to 1 with 0.5 in the middle. A window needing exactly the average number of cuts gets 2−1 = 0.5; one cut gets close to 1; twice the average gets 2−2 = 0.25.
  • It is the standard Isolation Forest score (Liu, Ting and Zhou, 2008), computed by scikit-learn and used unchanged.
  • Raw scores bunch together: the middle held-out window scores 0.386 (russellmitchell) and 0.375 (harrison). That is why step 4 turns s into a percentile.

On the page (step 3) the general formula is written as in the original Isolation Forest paper: s(x) = 2−E[h(x)] / c(n), with h(x) the cuts (ℓ here) and n the windows per tree (ψ here).

Read the other way round: cuts = −c(ψ) × log2 s. That is how the page turns the middle score 0.386 back into 18.2 cuts.

Step 2The effect on the forest's score

The last column of step 2. It explains a window; it changes no score and no rank.

effecti = s(x) − s(x with feature i replaced by mh,i)

Every symbol

x
The window's 14 model features, as the forest sees them. Four heavy-tailed ones are on a log scale, ln(1 + value): window duration, mean gap, shortest gap and alerts in the current entry. The other ten are used as they are. Night fraction is not among them.
mh,i
The median of feature i over this host's windows from the training days, on the same scale: 36 windows for russellmitchell's intranet server, 94 for harrison's. It is the column "host's baseline median" on screen.
s( · )
The forest's raw score from step 3: the same 200 trees, nothing refitted.
effecti
Positive: the window's real value makes it more unusual than the host's usual value would. Negative: the usual value would look odder to the forest.

How it is calculated, step by step

  1. Take the window's 14 values.
  2. Replace one of them by the host's median and keep the other 13. For russellmitchell's user change: "rule new to this host" goes from yes (1) to the host's usual no (0).
  3. Send the changed window through all 200 trees again and average the cuts: 5.52 instead of 4.81. Without the new rule the window is harder to set apart.
  4. Turn that into a raw score: 2−5.52 / 13.23 = 0.749.
  5. Subtract from the real score: 0.777 − 0.749 = +0.028. That is the effect.

This is done once for each of the 14 features. On screen the three largest effects are marked "top 3"; each bar is that effect as a share of the largest one in the window, and negative effects point to the left.

Why it is done this way, and what to keep in mind

  • The host's median is the reference because the question is "what if this feature were normal for this host?", the same comparison as the column beside it.
  • The effects do not add up. In russellmitchell the 14 effects sum to 0.118, but setting all 14 to the host's medians at once gives s = 0.642 (8.45 cuts), 0.135 lower. In harrison: sum 0.099, all at once 0.608, 0.163 lower. The forest judges the features together, so one feature at a time is only an approximation.
  • Negative effects appear when the host's usual value is rarer among all hosts' windows than the window's own value: the forest is one model for all hosts. The full answer is in the harrison guide, step 2, "Why is the effect negative for some features?".
  • It is worked out afterwards (3 Looking back) and only for the page: tools/ait_explain.py, explain(); the log scale is tools/window_builder.py, log_transform().

Step 4From s to Sseq, and the weight wh

Sseq = 100 × ( wh × own + (1 − wh) × pooled ),   wh = nh / (nh + 100)
own = #{ host's held-out windows with score ≤ s } / nh,   pooled = #{ all hosts' held-out windows with score ≤ s } / N

Every symbol

held-out windows
Windows from the training days that were not used to grow the trees. The trees have seen their own training windows, so scoring those would be biased; the held-out ones are a fair yardstick.
nh
How many held-out windows host h has: 32 for russellmitchell's intranet server, 87 for harrison's.
N
The held-out windows of all hosts: 17,265 | 40,366.
own, pooled
The share of those windows that score no higher than this window: the empirical percentile, once against the host itself, once against everyone.
wh
How much the host's own yardstick counts.
100 (n0)
The number of held-out windows at which both yardsticks count equally.

Why a percentile

Raw scores bunch together around 0.4 to 0.5, so a straight rescale would make every window look alike. A percentile says something plain: "this window is more unusual than X% of the normal windows we kept aside".

Why is the weight wh = nh / (nh + 100)?

There are two yardsticks, and each is good at one thing:

  • Own knows what is normal on this host, but with few windows it is coarse: with 32 windows one window is 3.1 percentile points, and anything above the highest gets 100.
  • Pooled is fine-grained (tens of thousands of windows) but describes other hosts' normal behaviour.

The weight decides how far to trust own, and n / (n + n0) is the classic answer: Bühlmann's credibility weight from insurance, where a small group's own claim rate is trusted in proportion to how much data supports it. It has the properties you want:

  • no history (nh = 0): w = 0, use the pool only;
  • nh = 100: w = 100 / 200 = 0.5, both count equally;
  • more history: w climbs towards 1, never quite reaching it: 1,000 windows give 0.91, 10,000 give 0.99;
  • it changes smoothly: no host jumps from one yardstick to the other.

Why 100. The paper calls n0 = 100 a default, and its parameter table reports that 30 and 300 gave results within one seed's standard deviation, so the choice does not drive the results.

One way to see why 100 is a sensible default (my reading, not stated in the paper): with 100 windows, own moves in steps of 1 percentile point, the first size at which it can just about tell the 99th percentile from the 100th.

Why not a hard switch. An earlier version used own above 500 windows and pooled below. The paper reports that the quiet hosts' benign windows then exceeded 99 in 36–100% of cases; the weight lowered that to 0–50% wherever a host had more than four such windows.

How long should the training period be?

Three requirements, from the paper and from this section: the forest needs 4,000 to 8,000 training windows (the paper's floor and target, after taking every 10th window); a quiet host needs about 100 held-out windows before its own yardstick counts half; and the period should cover a full week of normal rhythm. Step 5From alerts to a queue item

u = maxalerts a in g Sseq(a) / 100,   k = number of alerts in g
g (queue item)
All alerts of one rule on one host, as long as each follows the previous one within 24 hours. The analyst reads items, not single alerts.
u
The item's most unusual alert, as a fraction: Sseq 99 becomes 0.99. An alert whose window is too short to score counts as 50 (the baseline median).
k
How many alerts the item holds: 1 for the user change in both replays.

Step 5The surprise π

π(g) = −log10( 1 − uk ),   u capped at 0.99999 so π is at most 5

Read it in four steps

  1. A normal window scores below the u-th percentile with chance u. That is what a percentile means.
  2. k independent normal windows all score below it with chance uk.
  3. So 1 − uk is the chance that at least one of k normal windows would score this high: a p-value.
  4. −log10 counts its zeros: a chance of 0.001 gives 3, 0.00001 gives 5.

What it tells us

How unlikely it is that normal activity would produce an item like this, in zeros. It says how rare, not how dangerous:

If you are asked, in short: "The surprise says how unlikely it is that normal activity would produce this item, counted in zeros: 5 means one chance in 100,000, 2 one in 100. It combines how unusual the item's most unusual alert is with how many alerts the item has, so one extreme alert on its own counts far more than one extreme alert among thousands. It says how rare, not how dangerous: a benign alert can be just as surprising."

Why it has this shape

  • It corrects for the number of chances. One extreme window among 7,068 alerts is expected; one extreme window from a single alert is not. While k × (1 − u) is small, π ≈ (nines of u) − log10 k: every tenfold more alerts costs one point of surprise.
  • Its weak point: it counts every alert as an independent chance. The alerts of one item are near-copies: in harrison's scan item 384,448 of 384,473 have exactly Sseq 99.99868, and in russellmitchell's 7,058 of 7,068 have 100. So the size correction over-corrects for floods. The paper says so ("treats members as independent although their windows overlap"); its milder alternative, one chance per window length (k / 20), gives 0.65 and 2.45 instead of 0.003 and 1.17, and ranked worse on the tuning set: in the comparison of 12 October it gave the non-scan stages a worse mean rank on three of four tuning replays, because every item of up to 20 alerts can then reach the single-alert ceiling. On today's method it would move the user change from 3 to 5.5 (russellmitchell) and from 1.5 to 3.5 (harrison). If asked: "Because on the tuning replays it put the important steps later. In the comparison of 12 October, four tuning replays with five seeds each, counting every alert gave the non-scan stages, the user change, the sudo escalation and the exfiltration, a better rank on three of the four replays. Counting one chance per 20 alerts lets every item of up to 20 alerts reach the same ceiling as the single-alert user change, so the top gets crowded: on today's method the user change would fall from 3 to 5.5 here and from 1.5 to 3.5 in harrison. The full count is wrong in principle but worked better for the takeover steps; it was chosen on the tuning data, which repeats one attack pattern."
  • The cap: u at most 0.99999, so π at most 5. Why u is capped: the box below. The other cap, in the sequence term, is explained in the next section.
Why is u capped at 0.99999?

Because Sseq = 100 is common at the top, and it would break the formula: with u = 1, 1 − 1k = 0 for every k, and −log10 0 is infinite. The paper: "Since Sseq = 100 would make π(g) infinite, ug is capped". Two things would go wrong without it:

  • No number. An infinite surprise cannot be put on the 0 to 100 scale or added to the novelty term.
  • Size would stop mattering. Every item whose best alert reaches 100 would get the same infinite surprise, whatever its size. In russellmitchell 12 items reach 100, among them a flood of 7,068 web-server 400 errors, which would tie with the single user change.

Step 5The sequence term

seq(g) = 100 × min( 1, π(g) / λ ),   λ = 8 in practice seq = 12.5 × π
So the sequence term can never be 100?

Right. π is at most 5 because u is capped at 0.99999, so π / 8 is at most 0.625 and the sequence term at most 62.5. The min( 1, … ) never comes into play; the paper says so itself: "the sequence term lies in [0, 62.5], and λ acts as a scale rather than a cap". The code says the same (tools/ait_eval.py, the comment of surprise()).

  • If you are asked, in three sentences: "Sseq itself goes up to 100; 62.5 is the sequence term, 100 × π / 8. The surprise π is capped at 5, because Sseq = 100 only means that none of our 17,000 to 40,000 normal windows scored higher, and without the cap it would become an infinite surprise. So the top is 100 × 5 / 8 = 62.5. The 8 is a fixed scale set before the test, and since every item is on the same scale, the ceiling changes no rank."
  • If you are asked why λ is 8, in short: "λ only sets the scale of the sequence term: the surprise cannot pass 5, so with λ = 8 nothing is ever cut. 8 was the default fixed when the queue was built, before any tuning; the weights 0.8 and 0.2 were then tuned on the four tuning replays with λ = 8, and together they set the balance: one point of surprise is worth 10 priority points, a rule new to the host 20. λ = 4 was tried and vetoed, because the top items would all tie at 100, and 8 is the value in the pre-registration."
  • Why 8 and not 5, which would let it reach 100? The paper's parameter table lists λ = 8 as a default and reports that λ = 4 was vetoed by the tuning protocol. With λ = 4 every item with π of 4 or more would hit the cap and tie at 100, so the top of the queue would lose its order. λ = 5 was not reported.
  • λ and the weights set the balance between the two parts of the priority. With λ = 8 and weight 0.8, one point of surprise is worth 0.8 × 12.5 = 10 priority points, and a rule new to the host (20 points) is worth exactly 2 points of surprise.
Why is there a cap, min(1, …), if it never cuts anything? And would it be a problem if it did?

Why it is there. It keeps the sequence term between 0 and 100, like every other term of the priority, whatever λ is. That matters because λ was a tuning parameter: values below 5 were tried, and for them π / λ can exceed 1. The same capped form, 100 × min(1, −log10(…) / λ), is used by the risk accumulator, where λ = 4 does make it saturate. With the frozen λ = 8 it is only a guard: π is at most 5, so π / 8 is at most 0.625.

Yes, it would be a problem if it cut. Every item above the cap would be cut to the same 100 and tie, and the order among them would be lost. This is what that would do to the two replays (seed 0, ranks and α-nDCG@20 by the frozen metric code):

  • λ = 4 cuts 15 items in russellmitchell: all get priority 100 and share places 1 to 15, so all five attack stages land on rank 8 (the user change from 3, the sudo escalation from 15). In harrison it cuts 6: the user change falls from 1.5 to 3.5, although α-nDCG rises a little. The paper reports that the tuning protocol vetoed λ = 4.
  • λ = 5 is the border: the items at π = 5 reach the cap exactly, but nothing is cut. Any λ of 5 or more cuts nothing; it only changes how much surprise counts against novelty.
  • The five-way tie at 70 is not this cap. Those five items have exactly the same π = 5.00, from the cap on u; the sequence term only passes it on.

With λ = 3 one cut item in each replay has no novelty point, so it ties lower, at 80; that is why "items cut" and "top tie" differ there. This is a what-if on seed 0 of two replays; the veto in the paper was decided on the four tuning replays.

Could λ be 5 instead of 8? It would still cut nothing.

Mathematically, yes: π is at most 5, so with λ = 5 the cap is reached exactly but nothing is cut, the sequence term runs from 0 to 100, and the priority can reach 100 instead of 70. But λ is not only the cap. With the weights 0.8 and 0.2 fixed, it also sets how much surprise counts against novelty:

  • λ = 8: one point of surprise is worth 0.8 × 12.5 = 10 priority points, so the novelty flag (20 points) equals 2 points of surprise;
  • λ = 5: one point is worth 0.8 × 20 = 16, so novelty equals only 1.25 points of surprise. That is the same as keeping λ = 8 and moving the weights to about 0.865 and 0.135.

What it would change here. On the two demo replays, over all 5 seeds, α-nDCG@20 is identical in every seed (means 0.414 and 0.727). The only difference: harrison's DNS exfiltration would come two places later in 3 of the 5 seeds (28 to 30, 27 to 29, 28 to 30). On the four tuning replays, the weight tuning (run with λ = 8) found that 0.9 / 0.1, which gives surprise even more say than λ = 5 would, scored slightly lower than the adopted 0.8 / 0.2 (0.522 against 0.526, provenance/ait/weight_lab_verdict.txt); λ = 5 lies between the two.

Why it stays 8. The method was frozen before the test replays were run, and every result was produced with λ = 8. Changing a parameter after seeing results is what the pre-registration forbids, and the gain would only be cosmetic: ranks do not depend on whether the scale ends at 70 or 100.

If nothing is cut, how can a rank change?

Because the rank is the order of the priority, and the priority adds two parts: 0.8 × sequence term and 20 × novelty. Changing λ from 8 to 5 makes every point of surprise worth 16 instead of 10, while novelty stays at 20. So an item without a new rule but with more surprise can now pass an item with a new rule. It passes it when its surprise is higher by more than 20 / 10 = 2 points with λ = 8, but already by more than 20 / 16 = 1.25 points with λ = 5.

Ranks, ties and "stages in top 20"

rank of a tied item = ( first place + last place ) / 2

Items with exactly the same score are tied, and each gets the average of the places the group occupies: the place it would get on average if the tie were broken at random. Russellmitchell: five items at 70 hold places 1 to 5, so each gets 3; in Wazuh's queue 39 items at level 3 hold places 30 to 68, so each gets 49.

stages in top 20 = number of attack stages whose best item has rank ≤ 20
Then can more than 20 items count as "in the top 20"?

Yes. If the items at places 15 to 21 tie, each gets (15 + 21) / 2 = 18, and all seven count as in the top 20, although only six of them fit on the first 20 places. The opposite happens too: in russellmitchell's Wazuh queue the service scan is one of 13 items tied at places 17 to 29, so each gets 23 and none counts, although four of them fit.

So the count is blunt in both directions, which is why it is not the main score: α-nDCG@20 (next section) shuffles tied items and gives partial credit. In the two demo replays no tie crosses place 20 with an average at or below 20 (harrison's Wazuh tie of 15 fills places 6 to 20 exactly), so the first case does not occur on screen.

Is it a problem when place 20 cuts through a tie?

For the count of stages, yes, as above. For the main score, no: α-nDCG puts tied items in a random order 50 times and averages, so in each order only the items that land on places 1 to 20 earn credit, and a tie cut by place 20 gets credit in proportion to how often its items land inside. In the two replays this happens once: Wazuh's 13 items at places 17 to 29 in russellmitchell, four of whose places are inside.

Two things are worth knowing, though.

  • Order inside a tie matters most at the top, not at place 20. Our russellmitchell queue would score 0.543 if its five-way tie at 70 always fell the best way, and 0.352 if it always fell the worst way. The fair value is the expected one, 0.432.
  • The reported value is an estimate. 50 orders with a fixed seed make it reproducible, but another 50 orders would give a slightly different number. The table gives the range 95% of such averages fall in, and the expected value from 20,000 orders.

α-nDCG@20, the main score

gain(i) = Σstages s in item i gs × (1 − α)cs(i),   DCG = Σi = 1..20 gain(i) / log2(i + 1),   α-nDCG@20 = DCG / DCGideal
gs
The grade of a stage, fixed before any result: 3 for user change, sudo escalation and DNS exfiltration (control or data), 2 for password cracking, 1 for the three scans, 0 for benign.
α = 0.5
The second item of the same stage earns half, the third a quarter. Finding a new stage is worth more than finding the same stage again.
cs(i)
How many items above place i already hold stage s.
log2(i + 1)
The discount: place 1 counts fully, place 3 half, place 15 a quarter.
DCGideal
The DCG of the best possible order of the same items (built greedily, the standard approach). Dividing by it puts every queue on 0 to 1.
ties
Tied items are put in 50 random orders and the score is averaged, so a tied method gets its expected value, not a lucky order.

The two comparators

Wazuh: Srule = 100 × level / 15

Wazuh's own order: the rule level, 0 to 15, as a share. The user change has level 3, so 20.0, and ranks 49 (tie of 39) in russellmitchell and 39 (tie of 35) in harrison. With only a handful of levels in use, big ties are normal.

Risk-based alerting: risk = 0.9 × variety + 0.1 × rarity item = its highest alert, windows of the past day
variety
How many different rule types the same host raised in the past day, the nearer in time the more they count (a triangle weighting), on 0 to 1.
rarity
(N − 1) / (c + N − 2) with N = 1 + E: c is how often this rule type fired in the window, E how often it was expected to from the training days. A rule firing once gives 1.
0.9, 0.1
The weights, tuned on the four tuning replays (after Uetz et al. 2026 and their CATS tool; other modules got weight 0).

Two numbers that only explain

Neither changes a score or a rank.

effect of feature i = s(x) − s(x with feature i set to the host's median)

Step 2's last column. Positive: the window's real value makes it more unusual than the host's usual value would. Negative: the usual value would look odder to the forest, which compares against all hosts' windows. How it is calculated, with all 14 features of both walks: The effect on the forest's score.

benign windows above 99 = #{ benign windows after training with Sseq > 99 } / #{ benign windows after training }

Step 4's check, per host, using the labels to leave attack alerts out. On the training windows themselves about 1% of a busy host's windows score above 99; on a quiet host more, because one window is a big share: 2 of the 32 on russellmitchell's intranet server (6%), 2 of the 87 on harrison's (2.3%). A benign window can still hold attack alerts, which raises the share during an attack.
