\begin{abstract}
Security Information and Event Management (SIEM) systems generate far more alerts than analysts can investigate, and ranking those alerts by static rule severity does not reflect the operational risk of the underlying activity. Enrichment approaches attach attributes to each alert independently, which leaves them unable to distinguish an isolated event from the same event occurring within an attack. We present a context-aware prioritization layer for the open-source SIEM Wazuh that derives context across time within the alert stream itself. For each alert and each entity it concerns, the layer forms a bounded window of that entity's recent activity, with repeats of one rule collapsed into a single entry, encodes the window as a fifteen-feature vector computed from Wazuh alert fields alone, and scores it with an Isolation Forest trained without labels on benign activity and calibrated per host. The score is combined with rule severity and asset exposure in a transparent hybrid function, alerts are presented as repeat groups so that high-volume floods occupy one queue position, and a per-entity accumulator escalates sustained activity. We evaluate on the public, labelled AIT Alert Data Set, comprising eight simulated enterprise networks with multi-step attacks, and characterize false promotion on five weeks of alerts from a real workstation. A preliminary, untuned check on the eight AIT scenarios finds that rule severity ranks post-reconnaissance attack alerts no better than chance, while the window anomaly score separates them with an AUC above 0.97 in seven of eight scenarios.
\end{abstract}

\section{Introduction}

Security Information and Event Management (SIEM) systems are widely used in modern Security Operations Centers (SOCs) to collect, correlate, and analyze security events, but large alert volumes can overwhelm analysts and delay the investigation of high-risk incidents \cite{ref14}. A major limitation is that alerts are often ranked mainly by static rule severity or identifiers, which may not reflect the real operational risk of an event when factors such as asset criticality, user behavior, vulnerability exposure, timing, and surrounding attack patterns are considered. Prior research has therefore explored context-aware alert classification, adaptive SIEM correlation, contextual log filtering, reinforcement learning-based prioritization, and explainable graph-based triage to reduce alert fatigue and help analysts focus on alerts with greater security impact \cite{ref1,ref5,ref6,ref7,ref8}.

Wazuh provides a suitable base for this type of research because it already supports log analysis, endpoint monitoring, rule-based detection, vulnerability detection, threat intelligence integration, MITRE ATT\&CK-aligned evaluation, and active response workflows. Recent Wazuh-focused studies have explored real-time threat feed integration \cite{ref3}, MITRE ATT\&CK evaluation \cite{ref12}, and machine learning-based improvements to threat detection \cite{ref13}. However, many of these approaches focus mainly on detection accuracy, threat intelligence enrichment, or response automation. Less attention has been given to an additional Wazuh-based prioritization layer that uses created context to decide which alerts should be investigated first.

A prioritization layer that evaluates each alert independently cannot express the distinction that matters most to an analyst. Consider two alerts identical in every recorded field: Wazuh rule 60122 (a failed Windows logon), the same host, the same user, the same severity level. In the first case it is the only such alert for that user in six hours, a mistyped password. In the second it is the fortieth within ninety seconds, followed by rule 60118, a successful logon. The second is a successful password-guessing attack and the first is routine noise, yet no attribute enrichment separates them, because the difference does not reside in the alert. It resides in the sequence of alerts surrounding it.

This paper proposes a context-aware alert prioritization layer for Wazuh whose primary signal is derived across time within a single alert stream. The layer does not replace Wazuh's detection rules or introduce new detections; it consumes alerts that Wazuh has already raised and re-orders them. For each incoming alert it forms a bounded window of preceding alerts concerning the same entity, encodes that window as a feature vector, and rates it with an unsupervised anomaly model. That rating is combined with Wazuh rule severity and asset exposure in an interpretable priority score, transparent scoring being retained because analysts must be able to understand and challenge a ranking \cite{ref9,ref10}. A decaying per-entity risk accumulator then raises sustained activity to incident level.

We make four contributions. First, a system model for a Wazuh prioritization layer in which correlation is derived mechanically from the alert stream rather than authored in advance as rule thresholds, with alert, context and risk state separated so that every result can be reproduced by replaying an immutable alert log. Second, a temporal context feature set computed entirely from Wazuh alert fields, including an active-time correction that separates a host being switched off from an entity being quiet. Third, a scoring design combining a per-host calibrated anomaly score with rule severity and exposure while remaining inspectable term by term, together with a repeat-group queue and an accumulator designed against measured double counting. Fourth, an evaluation on a public labelled alert corpus, the AIT Alert Data Set \cite{ref21}, complemented by five weeks of benign alerts from a real workstation, with an ablation isolating the contribution of temporal context and comparators that test whether the learned model earns its place.

\section{Related Work}

\subsection{Rule-Based Correlation in SIEM Platforms}

Correlation is not absent from existing SIEM platforms. Wazuh supports composite rules through options such as \texttt{frequency} paired with \texttt{timeframe}, \texttt{if\_matched\_sid}, \texttt{if\_group}, and field constraints including \texttt{same\_source\_ip} and \texttt{same\_user}. These allow an analyst to express that a pattern spanning several events should raise a higher-severity alert. The limitation is not capability but authorship: each such rule requires someone to anticipate a specific pattern and encode a fixed threshold for it, so the system detects only what has already been imagined and written down. The approach proposed here is complementary rather than competing, forming a context window mechanically for every alert and learning what is unusual within it from observed data.

\subsection{Context-Aware Alert Prioritization}

Cinque et al. \cite{ref7} demonstrate contextual filtering and prioritization of application logs for situational awareness, establishing that context external to an individual record improves the assessment of that record. Suarez-Tangil et al. \cite{ref6} frame SIEM correlation as an adaptive process, arguing that static correlation cannot accommodate multi-step attacks. Roy and Balde \cite{ref1} apply large language models to context-aware alert classification, separating organizational context from fixed SIEM rules. These works establish the value of context but largely treat it as attributes attached to an alert, rather than as structure recovered from the alert sequence.

\subsection{Sequence Context and Alert Correlation}

DEEPCASE \cite{ref15} establishes the mechanism this work adopts. For each security event it constructs a window of preceding events from the same device and uses an attention-based encoder-decoder to identify which contextual events are relevant, then clusters the resulting attention vectors so that operators triage groups rather than individual events. It reports filtering of 86.72\% of events and a 90.53\% reduction in analyst workload. AlertPro \cite{ref5} extracts context features from alert sequences together with history features from previously investigated alerts, and reports that context features outperform features drawn from raw alert fields alone. Both confirm that the preceding-event window carries substantial discriminative signal. DEEPCASE, however, requires a volume of event data and a training budget that a small testbed cannot supply, and AlertPro depends on a continuous expert feedback loop.

\subsection{Machine Learning Applied to Wazuh}

Chamkar et al. \cite{ref13} apply machine learning to improve threat detection in Wazuh, and Al Siam et al. \cite{ref3} integrate real-time threat feeds with Wazuh for automated malware detection and response. Winkler and Sharma \cite{ref12} evaluate Wazuh against the MITRE ATT\&CK framework using adversary emulation. These works target detection accuracy or enrichment rather than the ordering of the resulting alert queue.

Closest to the present work, Alboushy et al. \cite{ref17} propose Smart-SIEM, which constructs a per-source-IP behavioural context vector from the most recent $N$ events within Wazuh and classifies web application attacks using a LightGBM and XGBoost cascade. An ablation over $N \in \{3,\dots,35\}$ identifies $N = 30$, and context features are reported to improve all eight algorithms tested by 0.25 to 0.35 $F_1$, leading the authors to conclude that the context vector rather than the choice of algorithm is the primary contribution. That finding directly motivates the ablation design used here. The present work differs in three respects. Smart-SIEM performs classification, whereas this work performs ranking and is evaluated with ranking metrics. Smart-SIEM is fully supervised and required a purpose-built corpus of 46{,}454 labelled events with synthetic oversampling, whereas the anomaly model proposed here is trained without labels on benign activity. Finally, Smart-SIEM operates on HTTP application-layer telemetry, while this work operates on the full Wazuh alert stream and adds an incident-level accumulation stage.

Graph-based approaches have also been applied to Wazuh telemetry: Chaurasia et al. \cite{ref4} predict attack paths from event correlation, and Pomsathit \cite{ref11} applies graph neural networks with continual learning to Wazuh EDR data. These are not pursued here; the project focuses on learned scoring of stream-local context.

\subsection{Risk-Based Prioritization and Human Feedback}

Malach et al. \cite{ref8} combine alert triage with explainable graph representations and Shapley-based attribution, reinforcing that analysts require reasons accompanying a ranking. Shamsi et al. \cite{ref9} present human-centric risk-based alert prioritization in Splunk, and operational risk-based alerting practice \cite{ref19} accumulates risk per entity and escalates when a threshold is crossed together with evidence from multiple distinct sources or techniques. Khayat et al. \cite{ref10} combine multiple alert features using ensembled deep learning and hybrid optimization. Jalalvand et al. \cite{ref18} adapt prioritization through learning to defer with analyst feedback, and their survey \cite{ref16} organizes prioritization approaches by the degree of human-AI teaming involved. Feedback-driven adaptation is treated here as future work.

\subsection{Labelled Alert Corpora}

Public intrusion datasets such as CICIDS2017 and UNSW-NB15 consist of network flow records rather than SIEM alerts and cannot be consumed by an alert-level layer. Landauer et al. \cite{ref21} release the AIT Alert Data Set (AIT-ADS): alerts produced by Wazuh, Suricata and AMiner when the logs of the AIT Log Data Set \cite{ref22} are replayed through them, covering eight simulated enterprise networks, each with several days of simulated user activity and one multi-step attack, with both time-interval and event-level labels. It was designed for alert aggregation and attack-graph research and, to our knowledge, has not been used to evaluate alert ranking. Wazuh-collected Windows datasets also exist \cite{ref23}, but their per-record labels are derived from the presence of ATT\&CK tags on the triggering rule, which our feasibility check (companion report, Section~S1) shows to be common in benign activity; we therefore do not use them as ground truth.

\subsection{Admission and Normalization (C1, C2)}

Not every Wazuh alert describes behaviour, and admitting those that do not corrupts the window features rather than merely diluting them. The admitted stream is
\begin{multline}
\mathcal{A} = \{\, a : \mathrm{grp}(a) \cap G_c = \emptyset, \\
\mathrm{mode}(a) \neq \texttt{scheduled},\ a \notin \mathcal{D} \,\},
\end{multline}
where $G_c$ = \{\texttt{sca}, \texttt{rootcheck}, \texttt{policy\_monitoring}, \texttt{ciscat}\} are configuration-assessment groups, whose ATT\&CK fields describe what a check mitigates rather than what anyone did; $\mathrm{mode}(a)$ is the file-integrity monitoring mode, excluded when \texttt{scheduled} because such an alert carries the time the scan ran rather than the time of the change (on the workstation, 1{,}190 registry alerts fell into four distinct minutes); and $\mathcal{D}$ is the set of duplicate ingestions, alerts that re-enter the stream through a second log path. In AIT-ADS every Suricata alert is ingested twice, once from \texttt{eve.json} and once from \texttt{fast.log}; the second copy is in $\mathcal{D}$.

Normalization projects each alert onto a fixed schema: rule identifier, level and groups; ATT\&CK techniques and tactics; timestamp; agent; source address; user; and an ingestion sequence number that totally orders alerts sharing a timestamp. Wazuh writes ATT\&CK tags in two shapes: detection rules use a nested \texttt{rule.mitre} object with tactic names, configuration checks use flat lists of identifiers. Both are read and tactics normalized to identifiers. Every Suricata alert reaches the layer under a single Wazuh rule (86601), so rule-based features cannot tell one network signature from another; in the preliminary check this is why the novelty flag could not single out the exfiltration's DNS signature. The layer therefore uses the Suricata signature identifier as the rule identity of these alerts (in shaw, 16{,}692 Suricata alerts carry ten signatures); it is a detector rule identifier, not log content, so the layer remains content-blind. Every result after the preliminary check uses it. No other content, such as command lines, paths or the raw log line, is read: the layer is content-blind by construction.

\subsection{Entity Resolution (C3)}

Each alert resolves to a set of entities $E(a) \subseteq \{\mathrm{host}, \mathrm{user}, \mathrm{srcip}\}$, the units over which context accumulates. The host is the monitored machine, mapped from the Wazuh agent through a frozen alias table so that a re-enrolled agent remains one entity. The user is taken, for Windows logon events, from the target account and otherwise from the subject account, with machine and service identities excluded and domain and case variants normalized. The source address is taken from the decoder's source field when routable. Table~\ref{tab:resolution} gives the measured resolution rates. Each corpus populates two of the three types, and the pair differs: the workstation has no network logons, and AIT's dominant benign alert, a mail-server login, records the account only in the raw line, which the layer does not read.

\subsection{Temporal Context Window (C5)}
\label{sec:window}

For an admitted alert $a$ and an entity $e \in E(a)$, the window could simply be the last $N$ alerts concerning $e$, as in DEEPCASE \cite{ref15} and Smart-SIEM \cite{ref17}. On a busy host that window is a few seconds of one repeated rule: with $N = 20$, 89\% of baseline host windows in the four tuning scenarios held a single rule, and one flood evicts everything that preceded it. The window is therefore built from \emph{entries} rather than alerts.

\textbf{Entries.} A \emph{run} of rule $r$ on entity $e$ is a maximal sequence of $e$'s admitted alerts with rule $r$ in which consecutive members are at most $\delta$ apart. An entry summarizes one run as
\begin{equation}
\varepsilon = \big(r,\ \max_{x} l(x),\ \textstyle\bigcup_x \mathrm{tech}(x),\ \bigcup_x \mathrm{tac}(x),\ \tau^{\mathrm{f}},\ \tau^{\mathrm{l}},\ k\big),
\end{equation}
its rule, highest level, ATT\&CK tags, first and last member times and member count. A new alert joins the most recent entry of its rule if $\tau(a) - \tau^{\mathrm{l}} \le \delta$, and otherwise opens a new entry; interleaved rules keep separate runs, and a run broken by a gap longer than $\delta$ is never rejoined. The window $W(e,a)$ is the last $N$ entries of $e$, ordered by $\tau^{\mathrm{f}}$, whose newest member satisfies $\tau(a) - \tau^{\mathrm{l}} < T$, and it contains the entry holding $a$. $N = 20$\prov{}, $\delta = 60$\,s\prov{} and $T = 24$\,h\prov{}; The companion feasibility report (Section~S1) gives the sweep over $N$ and $\delta$: it fixes $\delta$, but does not by itself choose between entries and alert windows. An alert resolving to two entities updates two windows.

The entry gap $\delta$ is easily confused with the queue's group gap $\Delta$. The queue's repeat groups (Section~\ref{sec:queue}) merge over $\Delta = 1$\,h because they serve display; entries keep $\delta$ short because their start times carry the timing features, and a long $\delta$ erases exactly the pacing those features measure. The sweep confirms this: at $N = 20$, raising $\delta$ from 60\,s to 900\,s lowered the mean AUC from 0.963 to 0.829.

\textbf{Active-time correction.} A workstation is switched off most nights, and a window built on the first alert of the morning would otherwise span the overnight gap (up to 23\,h on our workstation). The host being off is not the entity being quiet, and only the second is evidence. For each host $h$ the builder records, online, every gap longer than $G$ between consecutive alerts in $h$'s \emph{global} stream (all of its alerts, including those excluded at admission, which still prove the machine was on), giving a set of downtime intervals $I_h$. A gap is recognized when the first alert after it arrives, so the correction is causal. For consecutive entries $\varepsilon_i, \varepsilon_{i+1}$ of the window, with start times $\tau_i = \tau^{\mathrm{f}}(\varepsilon_i)$,
\begin{equation}
g_i = \tau_{i+1} - \tau_i - \sum_{[s,f] \in I_h} \big| [\tau_i, \tau_{i+1}] \cap [s,f] \big| ,
\end{equation}
the active gap between the starts of successive runs. Gaps lying wholly within downtime ($g_i = 0$ with downtime present) are omitted from the inter-arrival statistics, since they are not observations of the entity; counted as zero they would mimic two simultaneous alerts. $G = 1800$\,s\meas{} was measured on the workstation, where it separated 23 nightly shutdowns from awake activity. The correction exists for the workstation only: it is disabled for AIT-ADS, whose servers run continuously, so no AIT result depends on $G$.

\textbf{Features.} Table~\ref{tab:features} defines the fifteen features over entries. Volume, which collapsing removes from the window's length, is kept explicitly in features 4 and 13. Features 2, 11, 12 and 13 are $\log(1+x)$-transformed before modelling. The tracked tactic ordinal follows ATT\&CK's Enterprise matrix order, and \texttt{tactic\_progression} is a weak ordering signal only, since tactics are not strictly sequential.

\begin{algorithm}[t]
\caption{Online window construction for one admitted alert}
\label{alg:window}
\begin{algorithmic}[1]
\Require alert $a$; per-entity deques $Q$; per-host last time $L$ and downtime $I$
\State $h \gets \mathrm{host}(a)$ \Comment{runs for every alert, admitted or not}
\If{$\tau(a) - L[h] > G$} \State $I[h] \gets I[h] \cup \{[L[h], \tau(a)]\}$ \EndIf
\State $L[h] \gets \max(L[h], \tau(a))$; drop intervals in $I[h]$ ending before $\tau(a) - T$
\If{$a \notin \mathcal{A}$} \Return \EndIf
\For{$e \in E(a)$}
  \State $\varepsilon \gets$ newest entry in $Q[e]$ with rule $r(a)$
  \If{$\varepsilon$ exists and $\tau(a) - \tau^{\mathrm{l}}(\varepsilon) \le \delta$} \State absorb $a$ into $\varepsilon$
  \Else \State append a new entry for $a$ to $Q[e]$; evict the oldest while $|Q[e]| > N$ \EndIf
  \State drop entries with $\tau(a) - \tau^{\mathrm{l}} \ge T$
  \State $\phi \gets \textsc{Features}(Q[e], a, I[h])$ \Comment{Table~\ref{tab:features}}
  \State emit $(a, e, \phi)$, scoreable iff $\sum_{\varepsilon \in Q[e]} k(\varepsilon) \ge 3$
\EndFor
\end{algorithmic}
\end{algorithm}

\subsection{Sequence Anomaly Scoring (C6)}
\label{sec:iforest}

Component 6 converts a window vector into $S_\mathrm{seq} \in [0,100]$ using an Isolation Forest \cite{ref20} trained without labels on benign windows. Unsupervised learning is used because it needs no attack labels and can rank activity no label described; it is the established choice for this role in alert triage \cite{ref5}. A forest of $t$ trees is grown on subsamples of size $\psi$; each tree splits on a random feature at a uniformly random value until points are isolated, so a vector in a sparse region is isolated near the root. With $\ell(\mathbf{v})$ the path length and $c(\psi) = 2H(\psi - 1) - 2(\psi - 1)/\psi$ its expected value under unsuccessful search,
\begin{equation}
s(\mathbf{v}) = 2^{-\mathbb{E}[\ell(\mathbf{v})] / c(\psi)} .
\end{equation}

\textbf{Model scope and training set.} One forest is fitted per entity type, since host windows (dense, mixed) and address or user windows (sparse) follow different distributions. Successive windows of an entity share almost all of their entries, so the training set is the baseline windows subsampled at stride $s = 10$\meas{}, which in simulation also improved ranking by giving quiet periods proportionate weight. Where several hosts feed one forest, the training set is stratified so that each host contributes an equal share up to its available windows, preventing the most active machine from defining normal for all. Inputs are the fourteen model features of Table~\ref{tab:features}, with no further scaling.

\textbf{Hyperparameters.} $t = 200$ and $\psi = \min(4096, n)$\meas{}. The original setting $\psi = 256$ assumes anomalies form a dense cluster, which attack windows do not; in a simulation over ten seeds, $\psi = 256$ ranked attacks at AUC 0.926, below a Mahalanobis comparator (0.965), while $\psi = 4096$ reached 0.991. On the workstation the training target is 8{,}000 windows after striding, with a floor of 4{,}000\meas{}: in simulation, below about 2{,}000 the variance across seeds exceeded the effect the ablation is meant to measure. An AIT scenario's pre-attack period is fixed, so its training set is whatever that period provides: on the tuning scenarios 1{,}840--6{,}885 host and 583--3{,}874 source-address windows, all below the target and most below the floor. There the spread across seeds is reported rather than assumed; on the tuning set it was at most 0.025 in $\alpha$-nDCG@20. A forest is fitted only for an entity type with at least 200 training windows, which excludes AIT's user entities (5--26). Each seed is an independent replica, forest and calibration both; metrics are computed per seed and reported as mean $\pm$ standard deviation over ten seeds, never on scores averaged across seeds, which would amount to a larger forest and hide the variance.

\textbf{Per-host calibration.} Raw scores concentrate near 0.5, so a linear rescale would make the sequence term nearly constant. Scores are instead mapped through the empirical distribution of each host's own baseline windows,
\begin{equation}
S_\mathrm{seq}(a, e) = 100 \cdot \hat F_{h,k}\big( s(\phi(W(e,a))) \big),
\end{equation}
where $\hat F_{h,k}$ is fitted on the \emph{held-out} baseline windows of host $h$ and entity type $k$, those the stride left out of training, falling back to the type-level distribution when $h$ has fewer than 500\prov{} of them. Calibrating on the training windows themselves is biased, since the trees were grown from those points; in a synthetic check the bias was small (5.2\% rather than 5\% of unseen benign vectors above the 95th percentile, with twice the variance across seeds), but the held-out windows remove it at no cost, so the workstation's drift check measures behaviour rather than this artefact. $S_\mathrm{seq}$ is then uniform on benign data by construction, commensurate with the other terms, and expresses how unusual a window is \emph{for that machine}.

\textbf{Reduction and cold start.} An alert's score is the maximum over its entities, $S_\mathrm{seq}(a) = \max_{e \in E(a)} S_\mathrm{seq}(a,e)$, with the arg-max entity recorded for the explanation: an alert unremarkable for its host but highly unusual for its source address should rise. Windows representing fewer than three alerts are unscored, receive the baseline median 50, and are flagged so that the analyst sees ``no temporal evidence'' rather than ``normal''.

\textbf{Attribution.} For an alert an analyst opens, each feature $j$ is replaced by its baseline median and the drop in $S_\mathrm{seq}$ is reported; the three largest drops are shown.

\subsection{Hybrid Priority Score (C4, C7)}
\label{sec:hybrid}

Component 4 attaches attributes that do not depend on history, giving an exposure score $S_\mathrm{exp} \in [0,100]$ from asset role. In AIT-ADS the dataset authors name the host behind every agent, and the AIT-LDS description places each role in a network zone \cite{ref22}; we set
\begin{equation}
S_\mathrm{exp} = 100\,(c + x)/2,
\end{equation}
with exposure $x = 1$ for hosts reachable from the Internet (the DMZ servers and the firewall), $0.5$ for the intranet, reachable from outside only through the VPN, and $0$ for hosts the organization does not own; and criticality $c = 1$ for hosts that hold organizational data or control access, $0.5$ for the web server and $0$ for hosts not owned. This gives 100 for the VPN, mail and cloud-share servers and the firewall, 75 for the intranet server, the file share and the web server, and 0 for the external mail servers and global DNS. The table was fixed from the role descriptions before any ranking was computed with it. Neither corpus records vulnerabilities, and on the single-host workstation $S_\mathrm{exp}$ is constant. Component 7 combines
\begin{equation}
P(a) = w_r\, S_\mathrm{rule}(a) + w_c\, S_\mathrm{exp}(a) + w_s\, S_\mathrm{seq}(a),
\end{equation}
with $S_\mathrm{rule} = 100\, l(a)/15$ for rule level $l(a)$, linear so that each term's contribution can be displayed. The weights are selected on the tuning scenarios by the protocol objective (Section~\ref{sec:protocol}) over the weight simplex in steps of 0.1, together with an alternative $S_\mathrm{rule}$, the mid-rank percentile of the alert's level among its host's baseline alerts. The objective is maximized with $w_r = w_c = 0$: every configuration within 0.01 of the optimum has $w_r \le 0.1$ and $w_c \le 0.1$, and the former default $(0.3, 0.2, 0.5)$ scores 0.337 against 0.395 (companion report, Table~S3). On AIT-ADS the priority therefore reduces to the sequence term. The hybrid form is kept because it is what makes the terms inspectable and because a deployment with a real asset inventory may weight exposure differently, but the evaluation reports the tuned weights and the default side by side.

\subsection{Repeat-Group Queue (C9)}
\label{sec:queue}

An attack phase or a benign job can raise thousands of near-identical alerts; in AIT-ADS a single directory brute force produces over 400{,}000. Ranked individually they occupy the whole queue. The queue therefore ranks \emph{repeat groups}: maximal runs of admitted alerts with the same host and rule in which consecutive members are at most $\Delta = 1$\,h\prov{} apart. Each group is shown once, with its count and time span. Its priority must summarize up to hundreds of thousands of member scores. The maximum, first proposed, gives a group of $k_g$ members $k_g$ chances to draw a high score; we therefore score a group by the surprise of its maximum given its size, the same correction Component 8 applies to its window term (Section~\ref{sec:accum}),
\begin{equation}
\pi(g) = -\log_{10}\!\big(1 - u_g^{\,k_g}\big), \qquad u_g = \max_{a \in g} S_\mathrm{seq}(a)/100,
\end{equation}
how improbable it is that $k_g$ benign alerts would produce a maximum this high, left uncapped when ranking $S_\mathrm{seq}$ alone so that the top of the queue has no ties. Every member of a group shares its host and rule, so $S_\mathrm{rule}$ and $S_\mathrm{exp}$ are constant within it, and the group's hybrid priority is $w_r S_\mathrm{rule}(g) + w_c S_\mathrm{exp}(g) + w_s \cdot 100 \min(1, \pi(g)/\lambda)$, the sequence term on the same 0--100 scale as $q$ in Component 8, with $\lambda = 8$\meas{} selected on the tuning scenarios. On the tuning scenarios $\pi(g)$ raised the reciprocal rank of the non-scan stages above the maximum's for every window, and for entries raised $\alpha$-nDCG@20 from 0.264 to 0.395 (companion report, Table~S3). The choice of $n = k_g$ is empirical: it treats members as independent although their windows overlap, yet the better-motivated discount $n = k_g/N$ performed worse. Any size discount, like the maximum before it, can hide a single anomalous alert inside a large group of the same rule on the same host, so each queue item also shows its highest-scoring member. On the four tuning scenarios this reduces 13{,}877--466{,}383 alerts in the evaluation period to 90--191 queue items. Each queue item lists its three highest-contributing terms, the window features that most influenced $S_\mathrm{seq}$, the arg-max entity, and, for risk notables, the contributing groups.

\subsection{Entity Risk Accumulation (C8)}
\label{sec:accum}

Component 8 keeps a decaying risk total per entity so that a campaign of individually unremarkable alerts becomes visible. Summing $P(a)$ over alerts, as first proposed, measures volume rather than evidence: on a 300-alert sample it inflated host risk twentyfold, 93\% of it from one 23-second configuration scan. Three mechanisms cause this and each has a remedy.

\textit{Repeat inflation.} Identical alerts each contributed in full. Alerts are grouped into accumulation groups $g$ by (entity, rule), split when the rule is silent for longer than $T$, and a group of $k_g$ alerts contributes $(1 + \ln k_g)$ times one alert's value.

\textit{Window evidence charged per alert.} $S_\mathrm{seq}$ describes a window that persists across many alerts, so a single anomalous window was charged once per alert as it slid. The window term therefore enters as a decayed running maximum, not a sum.

\textit{Cross-entity fan-out.} An alert resolving to two entities raises two totals; totals are compared only within an entity type, and notables sharing contributing alerts are merged into one incident.

The accumulator is
\begin{multline}
R_e(t) = \sum_{g \in \mathcal{G}_e} v_g\,(1 + \ln k_g)\, 2^{-(t - t^{\mathrm{last}}_g)/h} \\
+ a_s \max_{a :\, t - \tau(a) < T} q(a, e)\, 2^{-(t - \tau(a))/h},
\end{multline}
with $v_g = a_r S_\mathrm{rule} + a_c S_\mathrm{exp}$ of the group's first member, $t^{\mathrm{last}}_g$ its most recent member, and half-life $h = 4$\,h\prov{}. The accumulator keeps its own weights, $(a_r, a_c, a_s) = (0.3, 0.2, 0.5)$\prov{}, separate from the queue's: the tuned queue weights give the static terms zero weight (Section~\ref{sec:hybrid}), which would leave the accumulator no group evidence at all. Decaying from the most recent member, and splitting groups at gaps longer than $T$, keeps a burst today from being absorbed into a group that began weeks earlier, which would otherwise make any repeat of a known rule contribute nothing.

The window term uses a surprise score rather than $S_\mathrm{seq}$ itself. Because $S_\mathrm{seq}$ is uniform on benign data, the maximum over many windows approaches 100 for any busy entity: a host producing hundreds of windows an hour would hold a near-constant window term. With $u = S_\mathrm{seq}(a,e)/100$ and $n_e$ the effective number of independent windows the entity produced in the preceding $T$,
\begin{equation}
q(a, e) = 100 \cdot \min\!\big(1,\ -\log_{10}(1 - u^{\,n_e}) / \lambda \big),
\end{equation}
the probability that $n_e$ benign windows would produce a maximum this high, expressed on a log scale saturating at $\lambda = 4$\prov{}. Successive windows overlap, so $n_e$ is not the window count. A window changes materially only when an entry is added to it, so $n_e$ is the number of entries the entity opened in the preceding $T$ divided by $N$; counting every window would treat each alert merged into a flood's run as a fresh draw and make $q$ near zero for any busy entity. (For the alert window of B2$_\mathrm{alert}$, $n_e$ is the window count divided by $N$.) Before use, the correction is validated on the workstation by checking that the window term is not flat for its host across a benign day.

\textbf{Escalation.} An entity becomes a risk notable when three conditions hold together: $R_e(t) > \theta$\prov{}, an amount of evidence; its contributing groups number at least two, so that one flood cannot escalate on its own; and they carry at least two ATT\&CK tactics contributed by \emph{different} rules. The last condition is a correction: several common benign rules each carry two or three tactics, so the original ``two tactics'' condition was met by a single benign alert. $\theta$ is calibrated as $S_\mathrm{seq}$ is, per entity type, as the 99.9th percentile of $R_e(t)$ over the baseline period, so that it states a benign crossing rate rather than a hand-set level. A group is \emph{contributing} only while its decayed term is at least 10\% of $R_e(t)$, so that a residue from the previous day cannot supply the second group.

\textbf{Notables in the queue.} A risk notable enters the queue as one item that absorbs its contributing groups, which are listed inside it rather than ranked separately, following risk-based alerting practice in which the incident, not its contributing events, is what the analyst triages \cite{ref19}. Its priority is placed on the queue's scale by the same device as $S_\mathrm{seq}$, the percentile of $R_e(t)$ among the entity type's baseline values. Since $\theta$ is the 99.9th percentile, a notable enters at 99.9 or above, in practice above nearly every group, and notables are ordered among themselves by that percentile. This is a working assumption; it is tested on the tuning scenarios against two alternatives, no absorption (each contributing group keeps its own position) and no promotion (a notable takes the priority of its best contributing group), by the first-item rank of non-scan stages on AIT-ADS and by notables per awake hour on the workstation.

\section{Evaluation Design}
\label{sec:eval}

\subsection{Datasets}

The two corpora have different roles and never meet. AIT-ADS is the primary corpus: every ranking result comes from it. The workstation is secondary: it contains no attacks and answers one question, how much benign activity on a real machine the layer would promote. Both pass through the same nine components, but each is replayed separately with its own fitted models; no alerts, windows, forests or calibration tables are shared or pooled. Only configuration crosses, in one direction: the weights, $\Delta$ and $\theta$ selected on the AIT tuning scenarios are applied to the workstation unchanged, so that its false-promotion figures describe the layer as it would be deployed. \textbf{AIT-ADS (primary)} \cite{ref21} provides the labelled evaluation. Each of its eight scenarios is a separate simulated organization of 9--11 monitored hosts with 1.9--4.3 days of activity before a multi-step attack of ten steps: network and service scans, directory and WordPress scans, a webshell upload, password cracking, a reverse shell, privilege escalation, a service stop, and DNS exfiltration. Of the ten steps, four (the network scan, webshell upload, reverse shell and service stop) raise no Wazuh or Suricata alert in any of the eight scenarios. Password cracking raises one only where it is performed online against a service (two of the seven scenarios that include it, through Suricata), and the exfiltration in two of eight. The directory and WordPress scans and privilege escalation raise alerts in all eight, the service scan in seven. A layer that re-ranks alerts cannot rank what was never raised, so stage coverage counts only stages with at least one alert, and the unalerted steps are reported as outside the layer's boundary rather than as misses. The gap lies in the rule set, not in the logs: the dataset's log-based anomaly detector, AMiner, run on the same raw logs, flags the webshell commands, offline password cracking and DNS scanning that Wazuh does not.

\textbf{Designed contamination.} The dataset authors start the DNS exfiltration at the beginning of every simulation, deliberately poisoning the training period of anomaly detectors \cite{ref22}. Whether this reaches the alert stream depends on whether a rule fires: in harrison and santos, a Suricata rule for DNS queries to a \texttt{.biz} domain raised 46{,}211 and 25{,}707 event-labelled exfiltration alerts \emph{before} the first attack step, 52\% and 49\% of their baselines; in the other six scenarios the exfiltration raised no alert at all. These two scenarios therefore test the layer under a heavily contaminated baseline, the risk that an unsupervised model learns an ongoing attack as normal. We report them as recorded, since a deployed layer cannot know its baseline is clean, and additionally retrain them with the labelled exfiltration alerts removed to measure what the contamination costs. The end of the exfiltration, which the authors intend as a detection target, produces an absence of alerts and is outside what an alert-ranking layer can observe.

\subsection{Systems Compared}

\begin{itemize}
\item \textbf{B0}: rule level. \textbf{B1}: B0 + exposure.
\item \textbf{B0$_\mathrm{rank}$}: B0 with the level replaced by its rarity, the percentile of the alert's level among its host's baseline alerts. It uses no temporal context, and on the tuning set it was the strongest system without it (companion report, Table~S3), so B2 must beat it, not only B0.
\item \textbf{B2}: B1 + sequence anomaly score; \emph{B2 vs.\ B1 isolates temporal context}.
\item \textbf{B2$'$}: B2 with the forest replaced by a robust z-score, $\max_j |z_j|$ against baseline medians: does the forest earn its place?
\item \textbf{B2$_\mathrm{nov}$}: B2 with $S_\mathrm{seq}$ replaced by the novelty flag alone: does the window add anything beyond ``never seen this rule here''?
\item \textbf{B2$_\mathrm{alert}$}: B2 with the window of the last 5 alerts, the strongest alert window on the tuning set, instead of entries: does collapsing change the ranking?
\item \textbf{B3}: B2 + entity accumulation.
\end{itemize}

\subsection{Protocol and Metrics}
\label{sec:protocol}

For each scenario, the forest and calibration are fitted on that scenario's activity before its first attack step and frozen; the evaluation period is the remainder. Scenarios are split before any tuning into a tuning set \{harrison, wheeler, russellmitchell, shaw\} and a test set \{fox, wilson, santos, wardbeck\}, each with two large and two small scenarios and one with exfiltration. All weights, $\Delta$, $\theta$ and the novelty and calibration choices are selected on the tuning set; every reported comparison comes from the test set. Ranking is measured over queue items. Ground truth comes from the event labels, graded by what the attacker's action achieved and fixed before any test result is seen (Table~\ref{tab:grades}): an item's grade is the highest grade among its members' stages, and benign items have grade 0. The grades derive from the attack steps described by the dataset authors and from nothing the layer reads, so no system is favoured by construction, as one would be if items were graded by rule level or by the ATT\&CK tags of the triggering rule.

\begin{itemize}
\item \emph{Graded $\alpha$-nDCG@k}, $k \in \{10, 20, 50\}$, the primary metric. With $g_s$ the grade of stage $s$ and $c_{s,i}$ the number of items above rank $i$ that contain $s$, the gain at rank $i$ is $\sum_{s \in i} g_s (1-\alpha)^{c_{s,i}}$, discounted by $\log_2(i+1)$ and normalized by the greedily computed ideal ordering \cite{ref24}. The factor $(1-\alpha)^{c}$, with $\alpha = 0.5$, credits the first item of a stage fully and each repeat less, so a scan that recurs on five hosts does not count five times. An item that bundles several stages earns each stage's gain at its rank, so risk notables, which absorb groups, gain from bundling as well as from position; first-item ranks are reported beside $\alpha$-nDCG for that reason.
\item \emph{First-item rank} of each non-scan stage and their mean reciprocal rank (MRR): how far the analyst scrolls before first meeting each stage that matters.
\item \emph{Stage coverage@k}, reported separately for non-scan and scan stages, since scans are surfaced by every system and would otherwise dominate.
\item \emph{Macro-AUC}: the alert-level AUC of each non-scan stage against benign alerts, averaged over stages so that a stage with thousands of alerts does not outweigh one with ten. It is queue-independent and secondary.
\end{itemize}
Ties are broken by average rank, the expected rank under random tie-breaking; this matters for B0, under which all groups of one rule level tie. Robustness is reported with binary grades and with grades (2, 1, 1), and with $\alpha = 1$, under which only the first item of each stage counts. The tuning objective, for weights, $\Delta$, $\theta$ and the remaining choices, is the mean $\alpha$-nDCG@20 over the tuning scenarios, ties broken by MRR.

\textbf{Statistics.} The test set holds about ten non-scan stage occurrences, so systems are compared \emph{paired} on the same stages: for each stage, the first-item rank under one system against the other, with the number improved and worsened and a Wilcoxon signed-rank test over the pairs. With ten pairs only a near-unanimous difference is significant, and the results are stated in those terms rather than as averaged percentages. Seeded systems are run ten times and enter the tests by their mean rank per stage.

\textbf{Accumulation (B3).} Notables are incidents and are measured as such: the time from the first attack step to the first notable containing an attack alert, the number of stages that notable spans, and on the workstation the number of notables per awake hour.

\textbf{Workstation.} The hold-out is the final week of the frozen baseline. Under stationarity 1\% of benign windows exceed the 99th baseline percentile; the observed share measures calibration drift, with a confidence interval from resampling whole days, since windows within a day are dependent. Analyst load is the number of queue items per awake hour, awake meaning outside detected downtime, whose priority exceeds a threshold fixed per system on the AIT tuning set: the priority above which half of the non-scan stages' first items fall.

\subsection{Threats to Validity}

AIT's users and attacks are simulated, its baselines are short (no weekly cycle) and its hosts are Ubuntu servers \cite{ref22}; the workstation supplies realistic benign activity but no attacks, so no single corpus provides both. Only 6--14 non-scan attack alerts exist per scenario, so per-stage ranks are reported for every scenario rather than averaged away. The scan stages are easy for every system and are reported separately. The workstation baseline spans an examination period with reduced use, and its agent was re-enrolled once, handled by the alias table. The queue is ranked over the whole evaluation period at once, whereas an analyst works a live queue in which an item from one day never competes with one from another; per-day ranking is reported as a check.

\subsection{Scope and Future Work}

The layer consumes alerts only and reads no log content, so its reach is bounded by the rule set: four of AIT's ten attack steps never enter it. Two extensions follow and are left to future work. First, AIT-LDS publishes the raw logs behind every alert \cite{ref22}, so window features could include each entity's log volume and its deviation from baseline; this needs no log content and would let an unalerted step show up as unusual context around the alerts that do fire. Second, a log-anomaly detector such as AMiner could be admitted as an additional alert source whose alerts enter the same windows as Wazuh's. Neither changes the layer's role: it ranks what detectors raise and does not itself detect.
